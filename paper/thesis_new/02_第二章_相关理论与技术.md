# 第二章 相关理论与技术

本章围绕“社区养老信息分发平台”的核心业务特征：跨端协同（B端管理+C端PWA轻应用）、多角色高自由度权限隔离（基于四表+菜单表的自定义RBAC，支持单用户多身份）、实时地理空间计算（基于射线法与BoundingBox优化的围栏匹配引擎，以及Haversine兜底）和高灵活度工程架构（逻辑外键设计、存储工厂模式）展开。核心目标是回答三个问题：为什么选这套技术、这套技术如何支撑需求、相比替代方案的工程取舍是什么。

## 2.1 跨端协同架构设计

### 2.1.1 B端：Vue 3与管理门户构建
对于B端管理门户，系统需要处理复杂的表单校验、动态菜单渲染、实时图表展示以及高德地图的深度集成。因此，前端技术选型采用了 Vue 3 + TypeScript 配合 Element Plus 组件库。

Vue 3 的 Composition API 极大地提高了复杂业务逻辑（如表单校验与地图组件封装）的可复用性。TypeScript 提供的静态类型检查机制，与后端 API（通过 axios 统一封装）形成了良好的类型契约，大幅降低了接口联调时的错误率。Element Plus 提供的现成组件（如表格、抽屉、弹窗）极大加速了管理门户的开发速度。

虽然 React 同样能胜任此工作，但在国内前端生态中，Vue 与 Element UI/Plus 的组合在开发中后台管理系统时拥有更丰富的现成解决方案和更低的学习成本。系统没有采用服务端渲染（SSR），而是采用单页面应用（SPA）模式，因为管理后台对 SEO 毫无要求，SPA 模式能够提供更接近桌面应用的交互体验。

### 2.1.2 C端：PWA与适老化轻应用
C端用户的核心需求是“即扫即用”和“低门槛”。如果开发原生的 iOS/Android 应用，开发成本高且老年人下载安装的门槛也极高；而传统的 H5 页面在离线状态下体验极差。

系统在C端选用了 PWA（渐进式 Web 应用）技术，通过 `vite-plugin-pwa` 插件自动生成 Service Worker。这套技术支撑了C端的几个核心需求：首先，用户只需扫描社区二维码即可直接打开网页，满足“即扫即用”；其次，PWA 支持将网页“安装”到手机桌面，形成类原生应用的体验；最后，通过配置 Workbox 的 `NetworkFirst` 缓存策略（API 请求缓存 1 小时）和 `CacheFirst` 静态资源缓存策略，即便在网络不佳的环境下，应用依然能展示骨架屏和缓存的业务数据，避免“白屏焦虑”。同时，通过 CSS 变量系统（`--font-size-base`），系统实现了三档（14px/16px/18px）字体的无刷新切换，完美契合适老化需求。

相比于开发微信小程序，PWA 技术完全脱离了微信的生态限制，保证了平台的独立性，且无需经过繁琐的应用商店审核流程。虽然 iOS 对 PWA 的支持不如 Android 完美，但在本项目的核心业务场景下（表单提交与状态查看），PWA 提供的离线体验和桌面留存能力实现了投入产出比的最大化。

## 2.2 多角色高自由度权限隔离

在社区养老场景中，角色的职责边界极其复杂。例如，“李阿姨”可能既是 C端的“老年人”用户，同时也是 B端的“社区志愿者（工作人员）”。此外，站长只能管理本站点的数据，而系统管理员则拥有全局权限。传统的“用户-角色”两表权限模型已无法支撑这种复杂的身份交织。

### 2.2.1 基于五表的自定义RBAC模型
为实现高自由度的权限隔离，系统摒弃了引入如 Casbin 这样厚重的第三方权限框架，而是自研了一套基于五表（`permissions`、`roles`、`role_permissions`、`user_identities`、`menus`）的自定义 RBAC 模型。

这套设计的核心支撑点在于 `user_identities`（用户-身份关联表）。它彻底替代了传统的 `user_roles` 表，使得一个用户（关联唯一手机号）可以拥有多条身份记录。每条身份记录绑定一个具体的 `role` 和 `station_id`。在权限检查流程中，系统会根据用户登录时激活的身份类型，查询其关联的所有角色，并对其权限（API 路径与方法）取并集。这一设计完美支撑了“一人多角”以及“站点级数据隔离”的复杂业务需求。此外，`menus` 表中的 `permission_code` 字段将前端动态菜单与后端权限代码紧密绑定，实现了从前端按钮级隐藏到后端 API 拦截的全链路安全闭环。

在开发初期，系统曾考虑使用 Casbin 框架。但 Casbin 复杂的模型配置文件和基于 CSV/DB 的策略存储，对于这种高度依赖动态查询（特别是需要连带查询站点 ID）的业务来说，维护成本过高。采用自定义的五表模型，虽然需要手写部分连表查询代码，但在 GORM Gen 的辅助下，降低了黑盒调试的成本，并获得了极大的业务定制自由度（例如硬编码放行 `Admin` 角色，提升了测试效率）。

### 2.2.2 JWT双端隔离机制
由于系统的 B 端和 C 端使用的是同一个底层的 `users` 数据表，如果 B 端的 Token 泄露，黑客可能用它来调用 C 端的接口，反之亦然。为了防止这种越权访问，系统在 JWT 中引入了严格的“端隔离”机制。

在签发 Token 时，JWT 的 Claims 载荷中除了包含常规的 `uid`、`exp`、`jti`（用于黑名单机制）等字段外，还强制写入了 `type` 字段（取值为 `b_end` 或 `c_end`）以及 `identities` 数组。在请求到达 API 前，路由中间件链会优先执行 `RequireEndType` 中间件，严格比对 Token 中的 `type` 是否与当前访问的路由分组（如 `/api/v1/b/*`）匹配。一旦发生端类型错配，请求将在权限验证发生前被立即拦截。

替代方案是为 B 端和 C 端颁发完全独立的鉴权体系（例如两套不同的秘钥），或者将两端拆分为微服务。考虑到系统的部署成本和运维难度，使用单体架构配合 JWT 载荷的 `type` 字段进行逻辑隔离，是在保证安全性的前提下，工程量最小、最高效的取舍。同时，配合 Redis 存储 `jti` 实现的单 Token 黑名单机制，弥补了 JWT 无法在服务端主动使其失效的先天缺陷。

## 2.3 实时地理空间计算

当 C 端用户提交服务需求时，系统必须在极短的时间内（毫秒级）根据用户的经纬度，判断其属于哪一个社区站点的服务范围，并完成订单派发。

### 2.3.1 基于射线法的地理围栏引擎
服务站点的覆盖范围在地图上表现为不规则的多边形（数据以 JSON 格式的顶点数组存储在 `service_zones` 表中）。系统在 Go 后端中自主实现了射线法（Ray Casting）算法判断用户坐标是否落入某个多边形内。射线法的原理是从待测点向右发射一条水平射线，统计该射线与多边形边界的交点数量，交点为奇数则在围栏内，偶数则在围栏外。由于不同站点的围栏可能会产生交叠，引擎还引入了优先级排序机制，优先匹配数值越大的围栏。

为什么不直接使用 MySQL 的空间扩展（如 `ST_Contains`）或引入专业的空间数据库 PostGIS？这是出于性能和部署成本的考量。频繁的数据库 I/O 和空间计算会带来性能瓶颈。因此，系统采用了“空间计算完全内存化”的工程策略，启动时将所有活跃的围栏数据加载到 Go 程序的内存中。
为了解决射线法遍历顶点计算带来的 CPU 消耗，系统引入了 BoundingBox（外包矩形）预过滤机制。引擎在初始化时为每个不规则多边形预计算出矩形边界。请求到来时，引擎首先使用时间复杂度极低的 `O(1)` 的矩形碰撞检测来快速排除无关围栏，只有少数候选围栏进入射线法计算。通过这种组合，系统将单次匹配耗时稳定控制在了低于 50ms。

### 2.3.2 Haversine 兜底规则
如果用户的定位由于 GPS 漂移等原因，落在了所有站点围栏之外的“真空地带”，系统引入了 Haversine 公式计算作为兜底方案。Haversine 公式能够在考虑地球曲率的前提下，精确计算出两个经纬度坐标之间的大圆球面距离。当射线法未能匹配到任何围栏时，引擎会遍历所有站点的中心坐标，计算出距离用户最近的站点，并强制将工单派发给该站点，保证了业务的连续性。

## 2.4 高灵活度工程架构

### 2.4.1 逻辑外键设计与 GORM DB First 模式
在数据持久化层面，本系统采用了 MySQL 8.0 结合 GORM Gen 工具的 DB First（数据库优先）开发模式。所有的表结构必须先在 `schema.sql` 中严格定义，随后由 GORM Gen 自动生成模型和查询代码（`.gen.go`），从根本上杜绝了代码与数据库结构不同步的问题。

虽然系统包含大量的关联关系（如需求关联用户、用户关联身份），但整个数据库中没有建立任何一条物理外键约束（Foreign Key Constraints），全部采用了逻辑外键设计。如果使用强物理外键，虽然能由数据库强制保证数据一致性，但在更新或删除数据时极易触发死锁，级联限制也会增加大批量数据清洗的难度。采用逻辑外键，将数据一致性的维护责任上移到 Go 语言的 Service 层，极大地解放了数据库的并发性能，并为后续系统向分布式数据库演进扫清了障碍。

### 2.4.2 存储工厂模式
平台涉及大量的业务凭证存储需求（如老人上传的健康证明图片等）。为了适应不同预算的部署环境，系统的 `storage` 模块采用了经典的工厂模式与接口抽象设计。

系统定义了统一的 `storage.Provider` 接口，并实现了两种底层驱动：基于 `os` 文件操作的本地存储（Local）和基于阿里云 SDK 的对象存储（OSS）。只需在环境变量中将 `STORAGE_DRIVER` 变量在 `local` 和 `oss` 之间切换，系统即可在启动时动态实例化相应的存储驱动。这种依赖倒置的设计，完美支撑了“低成本快速部署”的诉求：在预算有限的社区初期试点阶段，可以直接使用服务器本地存储；当平台需要接入 CDN 加速时，只需修改环境变量即可无缝迁移至阿里云 OSS，无需修改核心业务代码。

## 2.5 本章小结
本章围绕社区养老信息分发平台的业务特征，详细剖析了底层的技术选型与架构考量。为实现跨端协同，系统在前端选用了 Vue 3 与 PWA 的双模组合；为解决多角色隔离难题，设计了基于五表的自定义 RBAC 模型配合 JWT 的端验证机制；为攻克订单智能分发挑战，在 Go 内存中实现了包含 BoundingBox 优化的射线法与 Haversine 距离结合的空间计算引擎；在工程架构上，通过逻辑外键与存储工厂模式为系统的灵活部署和未来演进留足了空间。
