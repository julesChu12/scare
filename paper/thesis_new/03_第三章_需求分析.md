# 第三章 需求分析

## 3.1 可行性分析

### 3.1.1 技术可行性

本系统采用的技术栈均为业界成熟且广泛使用的开源技术。后端选用 Go 语言及 Gin Web 框架，Go 语言以其编译速度快、并发性能好的特点在 Web 服务端开发中得到广泛应用，Gin 框架则提供了完善的路由、中间件和参数校验机制。前端选用 Vue 3 框架并结合 TypeScript 进行开发，Vue 3 的组合式 API 使代码逻辑组织更加清晰，TypeScript 提供了静态类型检查，能够在编译阶段发现潜在的类型错误。数据库层面采用 MySQL 存储业务数据，Redis 用于缓存和 Token 黑名单管理，二者均是经过长期验证的成熟方案。地理围栏匹配所采用的射线法（Ray Casting）是计算几何领域的经典算法，原理成熟、实现难度适中、计算效率高。综上，系统所涉及的技术方案均具备良好的文档支持和社区生态，技术可行性较高。

### 3.1.2 经济可行性

系统开发所使用的编程语言、框架、数据库和开发工具均为开源软件，无需支付商业授权费用，开发阶段的软件成本为零。系统可部署在云服务器上，基础配置的云主机即可满足单街道试点阶段的运行需求，运维成本较低。同时，系统采用 Docker 容器化部署方案，降低了环境配置和后续迁移扩展的成本。因此，本系统在经济上是可行的。

### 3.1.3 操作可行性

C 端面向老年人及其家属，系统通过扫描二维码即可在手机浏览器中打开，无需安装额外应用，降低了操作门槛。需求提交流程设计为三步以内完成，界面元素采用大字体、高对比度的适老化设计。B 端管理后台提供站点管理、围栏管理、用户管理等可视化操作界面，社区工作人员经过简单培训即可上手使用。因此，本系统在操作上是可行的。

## 3.2 业务分析

### 3.2.1 现有业务流程

通过对霍营街道社区养老服务的实际运行情况进行调研，梳理出当前养老服务需求的处理流程如下。

**【请插入图片：图3-1 现有业务流程图 — 霍营街道社区养老服务现有流程示意图】**

老年人通过电话、微信群或线下到社区服务中心登记等方式提交服务需求。社区工作人员接到需求后，以人工方式进行信息整理和汇总，再根据个人经验判断该需求所属的服务区域，将其分配给对应服务站点的工作人员。服务人员接到任务后联系老年人并上门提供服务，服务完成后由工作人员手动更新需求的处理状态。

上述流程存在以下问题。第一，需求渠道分散，电话、微信群和线下登记三种方式并行，信息缺乏统一的归口管理，容易出现遗漏或重复。第二，响应时效低，从需求提交到派单完成依赖人工流转，受工作时间和人员在岗情况影响较大。第三，处理过程不透明，老年人提交需求后无法了解当前的处理进度和责任人，遇到问题也难以追溯。第四，派单缺乏空间依据，需求与服务站点的匹配主要依靠人工经验，未能充分考虑服务对象与各站点的地理位置关系。

### 3.2.2 目标业务流程

针对现有流程中存在的问题，系统上线后的目标业务流程设计如下。

**【请插入图片：图3-2 目标业务流程图 — 基于地理围栏的智能分发流程图】**

老年人或其家属通过扫描二维码访问 C 端系统，选择所需的服务类型并填写需求描述，系统在提交时自动获取用户的地理位置坐标。需求提交后，系统根据预先配置的地理围栏规则，自动将该需求匹配至对应的服务站点，并将其加入该站点的任务池。系统通过站内通知或邮件等方式告知站点工作人员有新的待处理任务。工作人员从任务池中认领任务后，联系老年人并上门提供服务。服务完成后，工作人员在系统中提交服务记录，系统自动通知老年人服务已完成，老年人可对本次服务进行评价。

与现有流程相比，目标流程通过统一的线上入口解决了渠道分散问题，通过地理围栏实现了需求与站点的自动匹配，通过任务状态的实时流转提高了过程的透明度。

### 3.2.3 用户角色分析

根据社区养老服务的实际参与方，系统的用户角色分为 C 端用户和 B 端用户两大类。

C 端用户是系统的服务对象，主要包括老年人和家属两种身份类型。老年人是养老服务的直接接受者，可自行通过系统提交服务需求、查看处理进度和评价服务质量。家属作为代理角色，可代替老年人操作系统、跟踪需求处理状态。此外，系统预留了孕妇、残疾人和儿童等身份类型，以满足社区内其他特殊群体的服务需求。

B 端用户负责系统的管理和服务提供，按权限级别分为三种角色。系统管理员拥有最高权限，负责服务站点的创建与维护、地理围栏的配置、用户账号和角色权限的管理。站点负责人管理其所属站点的日常运营，包括站内人员管理、任务的查看与分配、本站服务数据的统计分析。工作人员是一线服务提供者，主要职责为从任务池中认领待处理任务、上门为老年人提供服务，并在系统中提交服务完成记录。

## 3.3 功能需求

### 3.3.1 功能模块划分

**【请插入图片：图3-3 系统功能模块图 — 整体功能架构图】**

根据业务分析和用户角色的不同，系统的功能模块划分为 C 端和 B 端两部分。

C 端主要面向老年人和家属，功能模块包括以下四个方面。快速开通模块提供基于手机号和短信验证码的登录方式，用户首次登录时系统自动完成账号注册，无需额外的注册流程。需求提交模块支持用户选择服务类型、填写需求描述并上传图片，系统在提交时自动获取用户当前的地理位置坐标，用于后续的围栏匹配。需求管理模块允许用户查看已提交需求的列表和详情，了解每条需求的当前处理状态，并可对尚未受理的需求执行取消操作。服务评价模块在任务完成后开放，用户可对本次服务进行评分和文字评价。

B 端面向社区管理人员和服务人员，功能模块包括以下六个方面。任务管理模块是 B 端的核心，工作人员可查看所属站点的任务池，对任务执行认领、完成、转派等操作。站点管理模块支持管理员对服务站点进行新增、编辑和停用操作，站点负责人可管理本站的工作人员。围栏管理模块提供基于地图的可视化编辑界面，管理员可在地图上绘制多边形围栏区域，设置围栏的优先级和关联的服务站点。用户管理模块用于管理系统内所有用户的账号信息和角色分配。权限管理模块支持角色的创建和权限的配置，实现对不同岗位人员的访问控制。统计报表模块提供任务量、完成率、平均响应时长等维度的数据统计和图表展示，支持按时间范围和站点进行筛选。

### 3.3.2 地理围栏匹配流程

地理围栏匹配是本系统的核心功能之一，其作用是在用户提交服务需求时，根据用户所处的地理位置自动确定该需求应分发至哪个服务站点。

**【请插入图片：图3-4 地理围栏匹配流程图 — 匹配算法流程示意图】**

匹配过程分为以下步骤。首先，系统接收需求提交请求，从中获取用户的坐标信息（经度和纬度）。然后，系统从内存中加载所有处于启用状态的地理围栏数据，按优先级从高到低排列。对每个围栏，先进行最小外接矩形（BoundingBox）的快速筛选，将明显不在围栏范围内的坐标排除，以减少后续精确计算的次数。对于通过初筛的围栏，使用射线法逐一判断用户坐标是否位于该围栏多边形内部。一旦找到首个匹配的围栏，即返回其关联的服务站点 ID，并将需求分配至该站点的任务池。若遍历所有围栏均未匹配，则系统计算用户坐标与各站点的距离，选择距离最近的站点作为兜底分配方案。

## 3.4 非功能需求

### 3.4.1 性能需求

系统在性能方面需满足以下要求。地理围栏匹配作为需求提交的关键环节，单次匹配计算时间应控制在 50 毫秒以内，以保证需求提交的即时响应。系统各 API 接口的平均响应时间应不超过 500 毫秒。C 端页面的首屏加载时间应控制在 2 秒以内，减少用户等待时间。在单街道试点的使用规模下，系统的可用性应达到 99% 以上。

### 3.4.2 安全需求

系统在安全方面需要考虑身份认证、访问控制和数据保护三个层面。在身份认证方面，系统采用 JWT（JSON Web Token）进行用户身份验证，B 端和 C 端使用不同类型的 Token 进行隔离，防止跨端越权访问，同时引入 Token 黑名单机制支持用户主动登出和强制下线。在访问控制方面，系统基于 RBAC（基于角色的访问控制）模型实现细粒度的权限管理，支持同一用户绑定多个身份角色，不同角色对应不同的功能操作权限。在数据保护方面，用户密码使用哈希算法加密后存储，系统与客户端之间的数据传输采用 HTTPS 协议，敏感信息在接口返回时进行脱敏处理。

### 3.4.3 可用性需求

系统面向的主要用户群体为老年人及其家属，因此在可用性方面需特别注意适老化设计。界面应简洁直观，避免信息过载，核心操作按钮采用大尺寸和高对比度配色。需求提交的操作流程应控制在三个步骤以内，减少用户的学习成本。C 端采用 PWA（渐进式 Web 应用）技术，用户可将系统添加至手机桌面，获得接近原生应用的使用体验，并在网络不稳定时仍可访问已缓存的页面内容。

## 3.5 本章小结

本章从可行性、业务流程、功能需求和非功能需求四个方面对系统进行了需求分析。通过对霍营街道社区养老服务现有流程的调研和梳理，明确了当前流程中存在的需求渠道分散、人工派单效率低和处理过程不透明等核心问题。在此基础上，设计了基于地理围栏自动匹配的目标业务流程，划分了 C 端和 B 端的功能模块，提出了性能、安全和可用性方面的非功能需求。上述需求分析的结果将作为后续第四章系统概要设计的依据。
