# 第四章 系统概要设计

本章在第三章需求分析的基础上，从全局视角对昌平区霍营街道社区养老信息分发平台进行概要设计。主要内容包括系统架构设计、核心功能模块划分、数据库概念与逻辑设计、系统接口设计以及安全性设计。本章的设计成果将为下一章的系统详细设计与编码实现提供基础指导。

## 4.1 系统架构设计

### 4.1.1 总体架构设计

本系统采用主流的 B/S（Browser/Server，浏览器/服务器）架构，并严格遵循前后端分离的设计思想。系统整体划分为表现层（前端）、业务逻辑层（后端服务）和数据持久层（数据库与缓存），各层之间通过标准化的接口进行通信，从而降低系统的耦合度，提高可维护性和扩展性。

**【请插入图片：图4-1_系统架构图.png — 图4-1 系统总体架构图】**

1. **表现层（前端）**：分为 C 端用户端和 B 端管理门户。C 端面向社区老年人及家属，采用 PWA 技术，提供跨平台、免安装、支持离线访问的轻量级体验；B 端面向社区管理人员和工作人员，提供复杂的数据图表展示、地理围栏绘制、任务调度等高密度交互界面。
2. **业务逻辑层（后端）**：负责处理核心业务逻辑，包括地理围栏的射线法匹配算法、任务流转状态机、JWT 鉴权拦截、RBAC 权限校验等。后端服务以 RESTful API 的形式向前端提供数据接口。
3. **数据持久层**：主要负责业务数据的落盘持久化和高频访问数据的缓存。关系型数据（如用户信息、任务流转记录）存储于 MySQL；鉴权 Token 黑名单、系统会话状态等高频/临时数据存储于 Redis 缓存中，以减轻主库压力并提高响应速度。

### 4.1.2 技术栈选型

系统的技术选型综合考虑了开发效率、系统性能以及开源生态的成熟度。

**后端核心技术栈**

系统后端采用 Go 语言作为主要开发语言。Go 语言原生支持高并发（Goroutine），编译速度快，内存占用低，非常适合开发高性能 API 服务。Web 框架选用 Gin，它是 Go 生态中最成熟的轻量级框架之一，路由性能极高，中间件机制完善。数据持久层采用 MySQL 8.0 作为主数据库，配合 GORM ORM 框架进行数据操作，支持自动化数据迁移和代码生成。为了提高系统响应速度，引入 Redis 7.0 作为缓存中间件，用于存储 Token 黑名单和临时会话状态。在认证方面，系统采用 JWT（JSON Web Token）实现无状态鉴权，有效降低服务端会话存储压力，支持跨端独立鉴权。

**前端核心技术栈**

系统前端基于 Vue 3 框架构建，配合 TypeScript 进行静态类型检查，利用组合式 API（Composition API）提高代码逻辑复用性。构建工具采用 Vite 6.0，基于原生 ES 模块，冷启动极快，热更新（HMR）响应迅速。UI 组件库选用 Element Plus 2.5，这是一套企业级组件库，包含丰富的表格、表单、弹窗组件，极大提高了 B 端开发效率。状态管理采用 Pinia 2.1，它是 Vue 官方推荐的新一代状态管理库，全面拥抱 TypeScript，API 设计相较于 Vuex 更为直观。在地图服务方面，系统集成了高德地图 JS API 2.0，提供高精度的地图渲染与多边形绘制工具，完美契合地理围栏划分需求。

## 4.2 功能模块设计

基于第三章的需求分析，本系统主要划分为 C 端（用户服务）和 B 端（管理运营）两大功能子系统。

### 4.2.1 C 端用户模块设计

C 端主要面向社区老年人及家属，强调“适老化”和“低门槛”操作。功能模块包括：登录与身份模块，提供基于手机号+短信验证码的“免密快捷登录”，首次登录自动注册，支持用户在“老年人”和“家属”身份间灵活切换；需求提报模块作为核心业务入口，用户选择服务类型（如助餐、助洁、医疗陪护等），填写具体需求，系统自动获取当前经纬度并提交至后台；进度追踪模块以时间轴的形式展示需求的生命周期（已提交 -> 站点已接收 -> 专员已认领 -> 服务进行中 -> 服务完成），支持用户取消处于待处理状态的需求；服务评价模块在服务上门结束后，用户可对本次服务进行 1-5 星打分，并填写文字反馈以帮助站点提升服务质量。

### 4.2.2 B 端管理模块设计

B 端面向社区服务站长及工作人员，强调“高效协同”与“精细化管理”。功能模块包括：工作台大盘，通过 ECharts 提供可视化的数据看板，展示今日新增需求数、待分配任务数、超时告警等核心运营指标；任务分发与调度，工作人员可查看系统（通过地理围栏算法）自动分配到本站点的任务池，执行“认领”、“转派”、“标记完成”等操作，并上传服务留档照片；地理围栏管理，管理员可在内置高德地图上使用多边形工具绘制各服务站点的覆盖范围（Service Zones），并设置重叠区域的优先级；系统设置与权限，采用动态菜单和按钮级别的权限控制（RBAC），支持角色创建、权限细粒度分配、员工账号管理等。

## 4.3 数据库设计

数据库设计是计算机系统设计的核心环节，直接决定了系统的数据流转效率和数据一致性。本节对系统的概念结构和逻辑结构进行详细设计。

### 4.3.1 概念结构设计 (E-R 图)

根据系统业务逻辑，提取出系统的核心实体包括：用户（User）、角色（Role）、服务站点（Station）、地理围栏（Zone）、服务需求（Request）和任务分配（Task）。

**【请插入图片：图4-6 数据库E-R图 — 系统核心 E-R 图】**

实体间的核心关联关系如下：用户与角色为多对多关系（通过 `user_identities` 关联表实现，一个用户可在不同站点拥有不同角色身份）；站点与围栏为一对多关系（一个服务站点可管辖多个地理围栏区块）；用户与需求为一对多关系（一个用户可提交多次养老服务需求）；需求与站点为多对一关系（多个需求根据地理位置归属到同一个站点进行处理）；需求与任务为一对一关系（一个用户需求生成一条唯一对应的工作人员执行任务）。

### 4.3.2 逻辑结构设计 (数据表设计)

将上述概念结构转化为 MySQL 关系型数据库的物理表结构。遵循第三范式（3NF）设计原则，并采用逻辑外键以提升分布式场景下的扩展性能。以下为系统的核心数据表设计：

**用户基础信息表 (`users`)**

该表用于存储双端（B端与C端）用户的统一基础数据。主要字段包括：`id` 为主键，自增 BIGINT 类型，作为用户唯一标识；`phone` 为登录手机号，类型 VARCHAR(20)，设置唯一索引；`password_hash` 存储密码哈希值（bcrypt加密），类型 VARCHAR(255)，允许为空以支持 C 端免密登录；`name` 存储用户真实姓名，类型 VARCHAR(50)；`avatar` 存储头像 URL，类型 VARCHAR(255)；`status` 为账号状态字段，类型 VARCHAR(20)，取值为 'active' 或 'disabled'；`created_at` 为账号创建时间，类型 DATETIME；`deleted_at` 为软删除标志位，类型 DATETIME，设置为普通索引。

**角色定义表 (`roles`)**

基于 RBAC 模型设计的角色表。主要字段包括：`id` 为主键，自增 BIGINT 类型；`code` 为角色编码，如 admin, staff 等，类型 VARCHAR(50)，设置唯一索引；`name` 为角色显示名称，类型 VARCHAR(100)；`is_system` 为是否系统内置不可删角色标志，类型 TINYINT(1)，取值 0 或 1。

**服务站点表 (`service_stations`)**

主要字段包括：`id` 为主键，自增 BIGINT 类型；`code` 为站点编号，类型 VARCHAR(50)，设置唯一索引；`name` 为站点名称（如：霍营第一养老驿站），类型 VARCHAR(100)；`latitude` 为站点中心纬度，类型 DECIMAL(10,7)；`longitude` 为站点中心经度，类型 DECIMAL(10,7)；`contact_phone` 为站点联系电话，类型 VARCHAR(20)。

**地理围栏区域表 (`service_zones`)**

该表是地理围栏算法的核心数据来源。主要字段包括：`id` 为主键，自增 BIGINT 类型；`station_id` 为归属的服务站点 ID，类型 BIGINT(20)，作为逻辑外键；`name` 为围栏名称（如：回龙观东区片区），类型 VARCHAR(100)；`points` 为多边形顶点经纬度数组集合，类型 JSON；`priority` 为匹配优先级，类型 INT(11)，重叠时数值大者优先。

**服务需求记录表 (`service_requests`)**

主要字段包括：`id` 为主键，自增 BIGINT 类型；`request_no` 为自动生成的业务流水号，类型 VARCHAR(50)，设置唯一索引；`user_id` 为提报需求的用户 ID，类型 BIGINT(20)，作为逻辑外键；`station_id` 为匹配后的服务站点 ID，类型 BIGINT(20)，作为逻辑外键；`service_type` 为服务类型（日间照料/助餐等），类型 VARCHAR(20)；`status` 为需求状态（pending/claimed等），类型 VARCHAR(20)，设置普通索引；`description` 为用户填写的具体需求详情，类型 TEXT；`submit_lat` 为提交需求时的定位纬度，类型 DECIMAL(10,7)；`submit_lng` 为提交需求时的定位经度，类型 DECIMAL(10,7)；`rating` 为用户评分，类型 INT(11)，取值 1-5。

## 4.4 系统接口设计

### 4.4.1 API 设计规范

为保证前后端交互的统一性和代码的可维护性，本系统后端接口严格遵循 RESTful API 架构风格设计规范。

RESTful API 规范要求 URI 语义化，使用名词的复数形式表示资源（如 `/api/v1/b/requests`），不包含动词。HTTP 动词映射操作规范如下：使用 `GET` 查询资源、`POST` 新建资源、`PUT` 全量更新资源、`DELETE` 删除资源。

所有接口均返回统一的 JSON 数据结构，包含状态码信息（msg）与负载数据（data）。标准 JSON 响应结构示例：
```json
{
  "msg": "ok",
  "data": {
    "total": 100,
    "items": [ ... ]
  }
}
```

### 4.4.2 核心业务接口

系统涉及的核心 API 接口包括：

认证模块：`/api/v1/c/auth/quick-start` 接口，请求方式 POST，功能为 C 端用户通过手机号+验证码快速登录/注册，无需权限；`/api/v1/b/auth/login` 接口，请求方式 POST，功能为 B 端工作人员通过账号密码登录管理后台，无需权限。

地理服务模块：`/api/v1/c/geocode/reverse` 接口，请求方式 GET，功能为根据经纬度反向解析当前所处街道与地址，需要登录有效 Token。

需求管理模块：`/api/v1/c/requests` 接口，请求方式 POST，功能为用户提交服务需求，触发底层围栏匹配引擎，权限要求为 C 端登录用户；`/api/v1/c/requests/:id/rate` 接口，请求方式 POST，功能为老年人对已完成的服务进行评分与评价，权限要求为需求发起人。

任务管理模块：`/api/v1/b/tasks/pool` 接口，请求方式 GET，功能为工作人员获取本站点的待分配任务池列表，权限要求为 Staff 角色以上；`/api/v1/b/tasks/:id/claim` 接口，请求方式 POST，功能为工作人员认领某项待处理的养老服务任务，权限要求为 Staff 角色以上；`/api/v1/b/tasks/:id/complete` 接口，请求方式 POST，功能为工作人员上门服务完毕，上传照片并结单，权限要求为任务执行人。

地理围栏模块：`/api/v1/b/zones` 接口，请求方式 POST，功能为管理员在地图上绘制并保存新的地理围栏，权限要求为 Admin 角色。

统计报表模块：`/api/v1/b/statistics/dashboard` 接口，请求方式 GET，功能为获取管理首页的图表统计数据（完单率等），权限要求为 Station Manager。

## 4.5 系统安全性设计

### 4.5.1 JWT 双端鉴权隔离机制

系统采用无状态的 JWT（JSON Web Token）作为身份凭证。为了防止权限混淆，JWT Payload（载荷）中专门设计了 `type` 字段（取值为 `b_end` 或 `c_end`）。在 Gin 框架的中间件层，拦截器不仅会校验 Token 的数字签名和时效性，还会进行跨端越权请求拦截。例如：携带 `c_end` Token 的用户试图访问 `/api/v1/b/...` 接口时，拦截器将直接驳回请求，返回 403 Forbidden，有效防止了普通用户越权访问后台管理数据。同时结合 Redis 维护 Token 黑名单，实现了用户修改密码或离职后的强制下线功能。

### 4.5.2 RBAC 细粒度权限控制

B 端管理系统的权限体系摒弃了简单的硬编码判断，采用了计算机系统中广泛应用的成熟 RBAC（Role-Based Access Control，基于角色的访问控制）安全模型。模型结构建立 用户-身份(`user_identities`)、角色(`roles`)、权限资源(`permissions`) 及角色权限关联表(`role_permissions`) 的网状关系。系统定义了诸如 `module:resource:action`（如 `task:pool:view`）的细粒度权限码。当工作人员发起请求时，后端 `PermissionMiddleware` 会提取当前用户的角色集，查询其拥有的所有权限树，与当前请求的 API 所需权限进行比对匹配。未授权操作将在进入 Controller 层之前被直接阻断，全方位保障了核心数据的安全性。

## 4.6 本章小结

本章详细阐述了 sCare 社区养老信息分发平台的概要设计方案。首先确立了基于 Go+Vue3 的前后端分离总体架构，并详细说明了核心技术栈的选型及其理由；其次对 B 端管理门户和 C 端用户端的功能模块进行了拆分规划；最核心的部分展示了系统的 E-R 图，并以结构化描述的形式详细说明了用户表、需求表、任务表、地理围栏表等核心数据库表的约束与结构；最后对系统 RESTful API 的接口规范及 JWT、RBAC 等安全性防护设计进行了详细说明。本章的各项设计输出为下一阶段的详细设计与代码落地奠定了坚实的理论基础。
