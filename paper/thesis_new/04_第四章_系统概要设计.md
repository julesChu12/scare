# 第四章 系统概要设计

本章在第三章需求分析的基础上，从全局视角对昌平区霍营街道社区养老信息分发平台进行概要设计。主要内容包括系统架构设计、核心功能模块划分、数据库概念与逻辑设计、系统接口设计以及安全性设计。本章的设计成果将为下一章的系统详细设计与编码实现提供基础指导。

## 4.1 系统架构设计

### 4.1.1 总体架构设计

本系统采用主流的 B/S（Browser/Server，浏览器/服务器）架构，并严格遵循前后端分离的设计思想。系统整体划分为表现层（前端）、业务逻辑层（后端服务）和数据持久层（数据库与缓存），各层之间通过标准化的接口进行通信，从而降低系统的耦合度，提高可维护性和扩展性。

**【请插入图片：图4-1_系统架构图.png — 图4-1 系统总体架构图】**

1. **表现层（前端）**：分为 C 端用户端和 B 端管理门户。C 端面向社区老年人及家属，采用 PWA 技术，提供跨平台、免安装、支持离线访问的轻量级体验；B 端面向社区管理人员和工作人员，提供复杂的数据图表展示、地理围栏绘制、任务调度等高密度交互界面。
2. **业务逻辑层（后端）**：负责处理核心业务逻辑，包括地理围栏的射线法匹配算法、任务流转状态机、JWT 鉴权拦截、RBAC 权限校验等。后端服务以 RESTful API 的形式向前端提供数据接口。
3. **数据持久层**：主要负责业务数据的落盘持久化和高频访问数据的缓存。关系型数据（如用户信息、任务流转记录）存储于 MySQL；鉴权 Token 黑名单、系统会话状态等高频/临时数据存储于 Redis 缓存中，以减轻主库压力并提高响应速度。

## 4.2 功能模块设计

基于第三章的需求分析，本系统主要划分为 C 端（用户服务）和 B 端（管理运营）两大功能子系统。

### 4.2.1 C 端用户模块设计

C 端主要面向社区老年人及家属，强调“适老化”和“低门槛”操作。功能模块划分如下：

1. **登录与身份模块**：提供基于手机号+短信验证码的“免密快捷登录”，首次登录自动注册。支持用户在“老年人”和“家属”身份间灵活切换。
2. **需求提报模块**：核心业务入口。用户选择服务类型（如助餐、助洁、医疗陪护等），填写具体需求，系统自动获取当前经纬度并提交至后台。
3. **进度追踪模块**：以时间轴的形式展示需求的生命周期（已提交 -> 站点已接收 -> 专员已认领 -> 服务进行中 -> 服务完成），支持用户取消处于待处理状态的需求。
4. **服务评价模块**：服务上门结束后，用户可对本次服务进行 1-5 星打分，并填写文字反馈以帮助站点提升服务质量。

### 4.2.2 B 端管理模块设计

B 端面向社区服务站长及工作人员，强调“高效协同”与“精细化管理”。功能模块划分如下：

1. **工作台大盘**：通过 ECharts 提供可视化的数据看板，展示今日新增需求数、待分配任务数、超时告警等核心运营指标。
2. **任务分发与调度**：工作人员可查看系统（通过地理围栏算法）自动分配到本站点的任务池，执行“认领”、“转派”、“标记完成”等操作，并上传服务留档照片。
3. **地理围栏管理**：管理员可在内置高德地图上使用多边形工具绘制各服务站点的覆盖范围（Service Zones），并设置重叠区域的优先级。
4. **系统设置与权限**：采用动态菜单和按钮级别的权限控制（RBAC）。支持角色创建、权限细粒度分配、员工账号管理等。

## 4.3 数据库设计

数据库设计是计算机系统设计的核心环节，直接决定了系统的数据流转效率和数据一致性。本节对系统的概念结构和逻辑结构进行详细设计。

### 4.3.1 概念结构设计 (E-R 图)

根据系统业务逻辑，提取出系统的核心实体包括：用户（User）、角色（Role）、服务站点（Station）、地理围栏（Zone）、服务需求（Request）和任务分配（Task）。

**【请插入图片：图4-6 数据库E-R图 — 系统核心 E-R 图】**

实体间的核心关联关系如下：
* **用户与角色**：多对多关系（通过 `user_identities` 关联表实现，一个用户可在不同站点拥有不同角色身份）。
* **站点与围栏**：一对多关系（一个服务站点可管辖多个地理围栏区块）。
* **用户与需求**：一对多关系（一个用户可提交多次养老服务需求）。
* **需求与站点**：多对一关系（多个需求根据地理位置归属到同一个站点进行处理）。
* **需求与任务**：一对一关系（一个用户需求生成一条唯一对应的工作人员执行任务）。

## 4.4 系统接口设计

### 4.4.1 API 设计规范

为保证前后端交互的统一性和代码的可维护性，本系统后端接口严格遵循 RESTful API 架构风格设计规范：
1. **URI 语义化**：使用名词的复数形式表示资源（如 `/api/v1/b/requests`），不包含动词。
2. **HTTP 动词映射操作**：使用 `GET` 查询资源、`POST` 新建资源、`PUT` 全量更新资源、`DELETE` 删除资源。
3. **响应格式标准化**：所有接口均返回统一的 JSON 数据结构，包含状态码信息（msg）与负载数据（data）。

**标准 JSON 响应结构示例：**
```json
{
  "msg": "ok",
  "data": {
    "total": 100,
    "items": [ ... ]
  }
}
```

## 4.5 系统安全性设计

### 4.5.1 JWT 双端鉴权隔离机制

系统采用无状态的 JWT（JSON Web Token）作为身份凭证。为了防止权限混淆，JWT Payload（载荷）中专门设计了 `type` 字段（取值为 `b_end` 或 `c_end`）。
在 Gin 框架的中间件层，拦截器不仅会校验 Token 的数字签名和时效性，还会进行跨端越权请求拦截。例如：携带 `c_end` Token 的用户试图访问 `/api/v1/b/...` 接口时，拦截器将直接驳回请求，返回 403 Forbidden，有效防止了普通用户越权访问后台管理数据。同时结合 Redis 维护 Token 黑名单，实现了用户修改密码或离职后的强制下线功能。

### 4.5.2 RBAC 细粒度权限控制

B 端管理系统的权限体系摒弃了简单的硬编码判断，采用了计算机系统中广泛应用的成熟 RBAC（Role-Based Access Control，基于角色的访问控制）安全模型。
1. **模型结构**：建立 用户-身份(`user_identities`)、角色(`roles`)、权限资源(`permissions`) 及角色权限关联表(`role_permissions`) 的网状关系。
2. **拦截机制**：系统定义了诸如 `module:resource:action`（如 `task:pool:view`）的细粒度权限码。当工作人员发起请求时，后端 `PermissionMiddleware` 会提取当前用户的角色集，查询其拥有的所有权限树，与当前请求的 API 所需权限进行比对匹配。未授权操作将在进入 Controller 层之前被直接阻断，全方位保障了核心数据的安全性。

## 4.6 本章小结

本章详细阐述了 sCare 社区养老信息分发平台的概要设计方案。首先确立了基于 Go+Vue3 的前后端分离总体架构，并利用表格形式给出了详尽的技术栈选型及理由；其次对 B 端管理门户和 C 端用户端的功能模块进行了拆分规划；最核心的部分展示了系统的 E-R 图，并以标准数据字典表格的形式详细说明了用户表、需求表、任务表、地理围栏表等核心数据库表的约束与结构；最后对系统 RESTful API 的接口规范及 JWT、RBAC 等安全性防护设计进行了详细说明。本章的各项设计输出为下一阶段的详细设计与代码落地奠定了坚实的理论基础。
