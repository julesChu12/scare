# 第五章 系统详细设计与实现

本章在概要设计的基础上，详细论述了昌平区霍营街道社区养老信息分发平台的具体实现过程。主要内容涵盖开发环境与项目结构的搭建，以及登录鉴权、养老服务需求提交、基于地理围栏的需求智能分发、工作人员端任务流转、以及多渠道通知与评价报表等核心功能模块的代码级实现。

## 5.1 开发环境与项目结构

### 5.1.1 开发环境与工具链

为了保证系统开发的顺利进行以及后续部署的高效性，本课题综合选用了业界主流的软硬件开发环境。

**后端开发环境：**
* **编程语言**：Go 1.25，利用其原生的并发优势处理大量 API 请求。
* **开发框架**：Gin Web Framework 1.11，提供高效的路由与中间件支持。
* **数据存储**：MySQL 8.0（业务持久化数据）与 Redis 7.0（缓存与 Token 会话管理）。
* **依赖管理**：Go Modules。
* **代码生成与调试**：使用 GORM Gen 自动生成强类型的数据库操作代码，使用 Air 实现热重载开发。

**前端开发环境：**
* **运行环境与构建工具**：Node.js 18+ 与 Vite 6.0，提供极速的冷启动和热模块替换 (HMR) 体验。
* **编程语言与框架**：TypeScript 5.3 + Vue 3.4（组合式 API）。
* **UI 组件库**：Element Plus 2.5。
* **PWA 插件**：`vite-plugin-pwa`，用于赋予 C 端用户端离线缓存与安装到桌面的能力。

### 5.1.2 后端目录结构

后端采用基于领域驱动设计（DDD）理念的经典分层架构。根目录下的 `backend` 按照职责严格划分为不同的功能包：

## 5.2 登录鉴权与权限控制的实现

系统的安全性设计是整个平台的基石。鉴于系统分为面向老人的 C 端和面向工作人员的 B 端，本系统设计了严格的双端鉴权隔离与基于角色的访问控制（RBAC）机制。

### 5.2.1 B 端密码登录与 C 端验证码快速开通

B 端面向社区管理人员，采用传统的账号密码认证方式。前端在提交前将密码进行简单哈希，后端接收后通过 `bcrypt` 算法校验密码哈希值。

C 端面向老年人群体，为了降低使用门槛，摒弃了繁琐的“注册-设置密码-登录”流程，实现了“手机号+短信验证码”的一键快速开通。在后端 `c_auth_handler.go` 中，若检测到手机号不存在，则自动在 `users` 表和 `user_identities` 表中为其生成具有 `elderly`（老年人）身份的新账号，随后直接颁发 JWT 登录凭证，实现无缝的用户体验。

### 5.2.2 JWT 双 Token 机制与黑名单

为了实现系统无状态的高效横向扩展，鉴权采用 JWT（JSON Web Token）机制。后端在登录成功后，颁发 Access Token（短期有效）与 Refresh Token（长期有效）。

**1. 端隔离防御**
为防止 C 端用户窃取 Token 后越权访问 B 端接口，JWT Payload 中植入了 `type` 字段（`b_end` 或 `c_end`）。在 `RequireEndType` 中间件中进行严格校验：

```go
// internal/middleware/end_type.go
func RequireEndType(expectedType string) gin.HandlerFunc {
    return func(c *gin.Context) {
        userType := c.GetString("user_type")
        if userType != expectedType {
            c.AbortWithStatusJSON(403, gin.H{
                "msg": "端类型不匹配，拒绝跨端访问",
                "data": gin.H{"expected": expectedType, "got": userType},
            })
            return
        }
        c.Next()
    }
}
```

**2. Token 黑名单与即时注销**
JWT 一经签发，在过期前默认有效。为了支持用户主动退出和管理员强制下线功能，系统利用 Redis 实现了 Token 黑名单。当调用注销接口时，将 Token 的唯一标识符（JTI）及其剩余过期时间写入 Redis：`SETEX token:blacklist:{jti} {ttl} "1"`。每次 API 请求不仅校验 JWT 签名，还会访问 Redis 检查黑名单。

### 5.2.3 RBAC 权限校验与菜单动态过滤

B 端管理台采用基于角色的访问控制（RBAC）模型，支持细粒度的接口校验和页面元素展示。

**1. 后端 API 权限拦截**
后端实现了 `PermissionMiddleware`。该中间件首先提取 Token 中的用户角色列表，然后查询数据库或缓存中该角色所绑定的所有权限码（如 `task:pool:claim`）。若当前请求对应的权限码不在授权列表中，且当前用户非系统内置的 `admin` 角色，则直接返回 HTTP 403 拒绝服务。

**2. 前端动态指令控制**
为了在前端实现按钮级别的隐藏，系统编写了自定义 Vue 指令 `v-permission`。在 DOM 渲染阶段，若判断当前登录用户不具备指令传入的权限码，则直接移除该 DOM 元素。

```typescript
// frontend/management-portal/src/directives/permission.ts
import type { Directive, DirectiveBinding } from 'vue'
import { usePermission } from '@/composables/usePermission'

export const permission: Directive = {
  mounted(el: HTMLElement, binding: DirectiveBinding) {
    const { value } = binding
    const { hasPermission } = usePermission()
    
    if (value && !hasPermission(value)) {
      // 权限不足，直接从父节点移除元素
      el.parentNode?.removeChild(el)
    }
  }
}
```

## 5.3 养老服务需求提交模块的实现

### 5.3.1 扫码入口与 C 端页面适老化

为方便老年人操作，C 端采用 PWA 技术封装，并提供社区二维码扫码直达入口。针对老年人视力衰退的特点，系统引入了适老化字体系统。

在 `useFontSize.ts` 中，系统定义了小、中、大三个档位的字号枚举，并将用户的偏好持久化至 `localStorage`。全局的 CSS Variables 通过 `[data-font-size]` 属性选择器驱动：

```css
  --font-size-medium: 16px;
  --font-size-large: 18px;
  --font-size-base: var(--font-size-medium);

  --font-size-base: var(--font-size-large);

/* 全局字号随根变量缩放 */

```

### 5.3.2 需求填写、定位获取与提交入库

老年人在 C 端选择所需服务（如上门助洁）并填写描述后，前端会调用浏览器的 Geolocation API 静默获取当前的精准经纬度。
提交至后端 `RequestHandler` 后，参数校验通过，系统首先持久化数据至 `service_requests` 表，状态初始标记为 `pending`。紧接着，异步调用地理围栏匹配引擎，根据定位信息将需求分配给最近的驿站，并生成对应的任务记录。

## 5.4 基于地理围栏的需求分发模块的实现

地理围栏智能匹配是本系统的核心创新点，解决了传统人工派单模式下效率低、易分配错误的问题。

### 5.4.1 围栏数据管理与可视化编辑

在 B 端的 `MapPolygonEditor.vue` 组件中，系统通过 `@amap/amap-jsapi-loader` 异步引入高德地图 JS API 2.0，并挂载 `AMap.PolygonEditor` 插件。
管理员可以直接在可视化地图上拖拽顶点，绘制不规则多边形覆盖目标小区。绘制完成后，前端提取各个顶点的经纬度集合，转换为 JSON 格式通过 `/api/v1/b/zones` 接口保存至 MySQL 数据库的 `service_zones` 表中。

### 5.4.2 射线法匹配算法

当新的养老需求进入系统时，后端内存中的 `GeofenceService` 开始匹配工作。
为了判断用户当前经纬度所在的坐标点是否处于某个不规则多边形（地理围栏）内部，系统采用了计算几何学中经典的**射线法（Ray Casting Algorithm）**。

算法核心原理是：从目标坐标点向同一方向（通常取正右方即 X 轴正向）发出一条射线，计算该射线与多边形所有边界相交的次数。若交点数为奇数，则点在多边形内部；若为偶数，则点在多边形外部。Go 语言的具体实现封装于 `pkg/geo/polygon.go` 中：

```go
// PointInPolygon 判断点是否在多边形内（射线法实现）
func PointInPolygon(point Point, polygon []Point) bool {
	if len(polygon) < 3 {
		return false
	}

	inside := false
	j := len(polygon) - 1

	for i := 0; i < len(polygon); i++ {
		pi := polygon[i]
		pj := polygon[j]

		// 检查是否恰好在多边形边界线上
		if pointOnSegment(point, pj, pi) {
			return true
		}

		// 射线法交点判断逻辑
		intersects := ((pi.Lat > point.Lat) != (pj.Lat > point.Lat)) &&
			(point.Lng < (pj.Lng-pi.Lng)*(point.Lat-pi.Lat)/(pj.Lat-pi.Lat)+pi.Lng)
		if intersects {
			inside = !inside // 每次相交反转布尔值
		}
		j = i
	}

	return inside
}
```

为了提升高并发请求下的匹配效率，系统在启动时将所有围栏的坐标点集加载至内存，并预先计算了每个围栏的最小外接矩形（BoundingBox）。匹配时，优先通过 O(1) 复杂度的外接矩形校验（判断点是否在经纬度最大最小极值之间），只有通过初筛的请求才进入复杂的射线法计算，极大降低了 CPU 消耗。

### 5.4.3 无匹配围栏的兜底分配

由于实际业务场景中可能存在新覆盖小区尚未划定围栏、或用户在街道交界处定位产生微小偏移的情况。系统设计了完善的容错兜底机制。
当用户提交坐标未能命中任何一条配置的地理围栏时，系统将触发 Haversine 算法，计算地球表面两点间的大圆距离，遍历所有驿站的中心坐标，将任务分配给直线距离最近的服务站点：

```go
// HaversineDistance 计算地球上两点之间的球面距离
func HaversineDistance(lat1, lng1, lat2, lng2 float64) float64 {
	lat1Rad := lat1 * math.Pi / 180
	lat2Rad := lat2 * math.Pi / 180
	deltaLat := (lat2 - lat1) * math.Pi / 180
	deltaLng := (lng2 - lng1) * math.Pi / 180

	a := math.Sin(deltaLat/2)*math.Sin(deltaLat/2) +
		math.Cos(lat1Rad)*math.Cos(lat2Rad)*math.Sin(deltaLng/2)*math.Sin(deltaLng/2)
	c := 2 * math.Atan2(math.Sqrt(a), math.Sqrt(1-a))
	return 6371000 * c // 乘以地球平均半径(米)
}
```

## 5.5 工作人员端任务管理模块的实现

### 5.5.1 任务池查看与认领

任务成功分发到站点后，该站点的所有工作人员登录 B 端大屏即可在“任务池”视图中看到这条待处理数据。
当某位员工点击“认领”时，系统向 `/api/v1/b/tasks/:id/claim` 发起 POST 请求。在后端的 `TaskService.Claim` 方法中，系统利用数据库的乐观锁或事务机制确保该条任务不会被重复认领。一旦认领成功，该任务的 `status` 将变更为 `claimed`，且 `staff_id` 被更新为认领人，其他员工将无法操作此单据。

### 5.5.2 派单、转派与上门记录

在实际服务中，常出现老员工休假或单量过载的情况，此时站长需要通过转派功能进行干预。
`TaskService.Transfer` 方法负责处理此类逻辑。站长选择新的接收员工后，系统更新任务分配表的 `staff_id` 归属，并同步推送站内信通知给新接手的员工。
上门服务完毕后，员工操作“标记完成”。接口强制要求员工填写服务记录并上传现场服务照片（通过 `StorageService` 将图片上传至本地静态目录或云端 OSS），以防虚假上门，做到服务闭环留痕。

### 5.5.3 状态流转与历史追溯

为了确保操作透明和防扯皮，任何导致任务状态或归属人发生变更的操作，都会在 `task_histories` 事务表中插入一条详细的历史快照。
记录内容包括：`action`（执行动作，如 CLAIM、TRANSFER、COMPLETE）、`operator_id`（执行操作的人）、`status_before`（变更前状态）、`status_after`（变更后状态）。这为后续的绩效考评与客诉溯源提供了坚实的数据基础。

## 5.6 通知、评价与统计模块的实现

### 5.6.1 多渠道通知触发与发送记录

为提高业务的响应速率，系统实现了异步通知服务（`NotificationService`）。在业务主流程（如需求生成、任务完成）结束后，系统利用 Go 语言的协程（goroutine）非阻塞地发起通知推送，避免阻塞主业务接口。
通知渠道支持：
1. **站内信 (In-App)**：保存至 `notifications` 数据库表，供 C 端老人或 B 端管理员登录后在右上角消息中心查阅。
2. **电子邮件 (Email)**：当任务完成后，系统通过内置的 `smtp_sender.go` 构造带身份鉴权的 SMTP 报文，向配置了邮箱的用户或站长下发服务结单通知。

### 5.6.2 服务评价提交与展示

服务被标记为完成后，C 端用户的需求详情页将解锁“评价模块”。用户可提交 1-5 星评分与建议反馈。后端接收后更新 `service_requests` 表的相关字段，并将此评价反向关联至对应的 `task_assignments` 记录，供站长在 B 端报表进行人员月度星级排名。

### 5.6.3 数据统计仪表盘与报表导出

B 端的 Dashboard 工作台整合了统计面板功能。通过 `statistics/dashboard` 接口，后端对 `service_requests` 表进行多维度的 `GROUP BY` 聚合查询，返回诸如“今日需求数”、“不同服务类型占比饼图数据”、“近 7 日任务接单趋势折线图数据”等。
前端利用 ECharts 将返回的 JSON 数据渲染为可视化图表。同时，后端支持根据站长选择的时间维度，利用 `Excelize` 库将底层任务明细表生成 `.xlsx` 标准格式文件，通过字节流直接提供给前端下载导出。

本章围绕昌平区霍营街道社区养老信息分发平台的核心业务逻辑，详细剖析了各关键模块的具体技术实现细节。介绍了系统基于 Go 与 Vue3 构建的运行环境与清晰的工程目录结构；从代码层面深入讲解了 JWT 双端隔离防御机制与 RBAC 权限指令的拦截实现；针对 C 端着重展示了适老化配置与需求提交流程；针对系统亮点，不仅图文并茂地解释了基于射线法的地理围栏核心匹配算法原理，还公开了性能优化的预过滤机制与容错兜底的球面距离计算代码；最后详述了 B 端工作人员如何通过状态机完成派单流转以及异步通知架构的实现方式。本章内容全面印证了第四章设计方案的技术可行性，为整个系统的稳定落地提供了实践佐证。
