# 第二章 相关理论与技术

本章不对技术做百科式罗列，而是围绕“社区养老信息分发平台”的业务特征展开：多角色并发访问、站点级权限隔离、地理围栏实时匹配、双端（B端/C端）协同和低成本部署。核心目标是回答三个问题：为什么选这套技术、这套技术如何支撑需求、相比替代方案的工程取舍是什么。

## 2.1 后端技术

### 2.1.1 技术选型原则

本课题后端选型遵循四项原则：

1. **并发与响应优先**：高峰时段需要同时处理登录、派单、任务更新与通知，要求服务具备较高并发处理能力。
2. **工程实现可控**：毕业设计周期有限，技术栈需要具备清晰的分层模式和成熟社区实践，避免在基础设施上投入过多时间。
3. **部署与运维简单**：目标环境以单机或轻量容器部署为主，要求构建、发布和迁移成本可控。
4. **可扩展性明确**：后续可平滑扩展至消息队列、对象存储、分布式缓存等能力。

### 2.1.2 Go + Gin 的适配性分析

后端采用 Go 语言和 Gin 框架。Go 的 goroutine 和 channel 机制天然适合 I/O 密集型 Web 场景；Gin 的中间件链路可直接承载认证、权限和审计逻辑。[6][7]

与常见替代方案对比：

| 方案 | 优势 | 局限 | 本课题结论 |
|------|------|------|-----------|
| Java Spring Boot | 生态成熟、企业实践多 | 资源占用较高、开发与部署链路相对重 | 不作为首选 |
| Node.js + Express | 上手快、前后端同语系 | 大型业务下类型与架构约束较弱 | 适合原型，不是本课题最优 |
| **Go + Gin** | 高并发、二进制部署、路由性能好 | 生态相对 Spring 简化 | **最终采用** |

因此，本系统在 Handler-Service-Repository 分层下，以 Gin 实现路由与中间件，以 Go 实现核心业务逻辑与并发处理。

### 2.1.3 GORM 与数据访问层设计

系统选择 GORM 作为 ORM 工具，并结合 GORM Gen 生成类型安全查询代码，原因如下：[8]

- 可在毕业设计周期内快速完成模型映射与 CRUD 开发；
- 支持事务控制，便于实现任务认领、状态流转等一致性场景；
- 与分层架构结合紧密，Repository 层职责边界清晰。

本课题不直接手写大量原生 SQL，而是在关键路径（分页查询、索引字段检索）保留 SQL 可控性，在日常业务中保持开发效率与可维护性平衡。

## 2.2 前端技术

### 2.2.1 Vue 3 + TypeScript

平台包含 B 端管理门户与 C 端用户端，两端共享业务模型但交互形态差异较大。Vue 3 的 Composition API 有利于按“认证、权限、请求、地图”拆分复用逻辑，TypeScript 则用于约束 API 契约，降低接口联调中的字段错误。[9][10]

### 2.2.2 Element Plus 与双端界面策略

B 端强调信息密度、表格操作和权限控制，采用 Element Plus 可快速落地后台常用交互（表格、表单、分页、弹窗），并统一视觉规范。C 端强调易用性与移动场景，保持轻交互和少步骤操作。[11]

### 2.2.3 PWA 的业务价值

社区养老服务存在网络不稳定与老年用户设备条件差异的问题。PWA 通过 Service Worker 提供基础离线能力和安装能力，可降低“页面打不开、重复登录、弱网提交失败”等体验风险。对本课题而言，PWA 不是功能炫技，而是可用性补偿机制。[25][26]

## 2.3 数据库技术

### 2.3.1 MySQL 的关系建模适配性

系统核心对象（用户、身份、站点、围栏、需求、任务、权限）天然具备强关联关系，且需要事务一致性，因此采用 MySQL 作为主存储。通过 InnoDB、utf8mb4、索引策略支持业务数据的可靠存储与检索。[12]

### 2.3.2 Redis 的缓存与状态管理角色

Redis 在本系统中承担“状态型数据”而非“主业务数据”存储，主要用于：[13]

- Token 黑名单（实现登出后即时失效）；
- 权限与会话短时缓存；
- 高频读取场景的访问加速。

MySQL 与 Redis 的组合使系统形成“主数据持久化 + 热数据加速”的分层数据策略。

## 2.4 安全技术

### 2.4.1 JWT 双端认证模型

系统采用 JWT 作为无状态认证载体，并在 Claims 中加入端类型字段（`b_end` / `c_end`），实现 B 端与 C 端访问隔离。该设计可避免“同一 token 跨端误用”的权限风险，并降低会话存储压力。[14][15]

### 2.4.2 RBAC 权限控制模型

本课题采用自定义 RBAC 三表模型（`permissions`、`roles`、`role_permissions`），并结合用户身份表支持多身份绑定。相比“仅靠前端路由控制”的简化方案，RBAC 模型可将权限约束前移到服务端，提升安全性和可审计性。[16][17]

### 2.4.3 认证与授权协同机制

JWT 解决“你是谁”，RBAC 解决“你能做什么”。两者通过中间件链路串联：认证通过后再做权限判定，形成分层防护。该机制与本系统多角色、多端点、站点化管理场景高度匹配。

## 2.5 核心算法

### 2.5.1 地理围栏匹配算法（Ray Casting）

系统采用射线法判断用户坐标是否落在多边形围栏内。为满足实时分发需求，采用如下优化路径：[18][19][20]

1. **BoundingBox 预过滤**：先进行外接矩形快速排除；
2. **优先级排序匹配**：按围栏优先级降序尝试匹配；
3. **内存预加载**：系统启动时加载活跃围栏，避免频繁数据库读取。

在围栏数量有限但调用频繁的社区场景中，该方案可兼顾准确性与响应速度。

### 2.5.2 Haversine 兜底算法

当坐标未命中任何围栏时，系统以 Haversine 公式计算用户到各站点球面距离，选择最近站点作为兜底分配结果。该策略避免“需求无法派发”的业务中断，保证服务闭环。[18][20]

## 2.6 本章小结

本章从“需求驱动”的角度说明了关键技术选型依据：后端采用 Go + Gin + GORM 支撑高并发与快速开发，前端采用 Vue 3 + TypeScript + Element Plus + PWA 支撑双端体验与可维护性，数据层采用 MySQL + Redis 形成持久化与缓存分层，安全层采用 JWT + RBAC 构建认证授权闭环，算法层采用 Ray Casting + Haversine 保证分发准确与业务连续。上述技术论证为第三章需求分析和第四章系统设计提供了可落地的理论与工程基础。
