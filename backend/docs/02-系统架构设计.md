### 1.2 技术选型变更说明

#### 1.2.1 数据库模式：Code First
*   **策略**: 使用 GORM 的 `AutoMigrate` 功能作为数据库表结构的**单一事实来源**。
*   **优势**: 开发迭代快，模型定义与代码逻辑强绑定。
*   **约束**: 
    *   **禁用 ENUM**: 数据库使用 `VARCHAR` 或 `TINYINT`，应用层常量控制状态。
    *   **禁用 Spatial Types**: 数据库不使用 `POLYGON` 等空间类型，兼容性更好，迁移更方便。

#### 1.2.2 地理围栏匹配：内存计算
*   **存储**: 围栏顶点坐标以 `JSON` 格式存入 MySQL。
*   **加载**: 服务启动时，读取所有活跃围栏加载至内存。
*   **匹配**: 使用 **Go 语言实现的射线法 (Ray Casting)** 进行点在多边形内的判断。
*   **性能**: 对于社区级应用（围栏数量 < 1000），内存匹配速度（微秒级）远快于数据库空间查询（毫秒级）。

## 2. 功能模块设计

### 2.1 需求采集模块

*   **输入**: 用户提交 `lat/lng` 坐标。
*   **处理**: 
    1.  校验坐标有效性。
    2.  存入 `service_requests` 表 (DECIMAL字段)。
    3.  触发分发引擎。

### 2.2 地理围栏分发模块 (核心变更)

#### 2.2.1 匹配流程

```
需求提交 (包含 lat, lng)
    ↓
应用层获取内存中的围栏列表 (List/R-Tree)
    ↓
[Go Routine] 遍历围栏:
    如果是候选围栏 (Bounding Box 初筛):
        执行 PointInPolygon(point, polygon_vertices)
    ↓
找到匹配的 StationID
    ↓
更新需求状态 -> Dispatched
```

#### 2.2.2 算法实现 (Go)

```go
// 围栏数据结构 (内存)
type InMemoryZone struct {
    ID        int64
    StationID int64
    Priority  int
    Polygon   []Point // 解析自数据库 JSON
    Box       BoundingBox // 预计算边界框
}

// 匹配逻辑
func (e *Engine) Match(lat, lng float64) int64 {
    point := Point{X: lat, Y: lng}
    
    // 1. 简单的线性遍历（数量少时最快）
    // 也可以使用 R-Tree 优化
    for _, zone := range e.zones {
        if zone.Box.Contains(point) {
            if RayCast(point, zone.Polygon) {
                return zone.StationID
            }
        }
    }
    return DefaultStationID
}
```

## 3. 代码组织规范与优化

### 3.1 接口文档 (Swagger)
*   **原则**: 代码即文档。
*   **工具**: 使用 `swag` 工具，通过 Controller 层的注释生成 OpenAPI 规范。
*   **位置**: `docs/swagger/`。
*   **访问**: `/swagger/index.html`。

### 3.2 目录规范
*   `internal/domain`: 定义 GORM 模型（Entity）。
*   `internal/dto`: 定义 API 请求/响应结构体。
*   `internal/service`: 业务逻辑（如围栏匹配算法）。
*   `internal/handler`: HTTP 处理与 Swagger 注释。
