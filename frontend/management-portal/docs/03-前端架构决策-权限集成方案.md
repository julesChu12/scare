# 前端架构决策：B端与管理后台集成方案

**文档版本**：v1.0
**决策日期**：2026-01-14
**决策状态**：✅ 已确认采纳

---

## 一、决策背景

### 1.1 问题描述

在设计社区养老信息分发平台前端架构时，面临B端（工作人员界面）与管理后台（系统管理）的组织方式选择：

**方案A**：分离为两个独立应用（`b-end` + `admin`）
**方案B**：集成为统一管理门户（`management-portal`），通过 Casbin 权限控制

### 1.2 角色体系分析

系统涉及3类管理角色，呈现**递进式权限关系**：

```yaml
角色层次:
  系统管理员 (admin)
    ↓ 拥有全部权限
  站点负责人 (station_manager)
    ↓ 拥有站点管理权限 + 工作人员权限
  普通工作人员 (staff)
    ↓ 仅拥有任务操作权限
```

**关键观察**：
- 权限呈现包含关系，非互斥关系
- 用户可能经历角色升级（工作人员 → 站点负责人）
- 功能模块存在大量重叠（任务管理、数据统计、通知等）

## 三、决策理由

### 3.1 权限模型天然匹配（核心理由）

Casbin 的 RBAC 模型与系统角色体系完美契合：

**Casbin 策略配置**：
```ini
# model.conf
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```

**权限策略示例**：
```ini
# policy.csv

# 角色继承（站点负责人继承工作人员权限）
g, station_manager, staff

# 工作人员基础权限
p, staff, /tasks, read
p, staff, /tasks/:id, claim
p, staff, /tasks/:id, complete
p, staff, /my-tasks, read
p, staff, /notifications, read

# 站点负责人额外权限（继承 staff + 新增权限）
p, station_manager, /station/:id/tasks, read
p, station_manager, /station/:id/staff, manage
p, station_manager, /tasks/:id, assign
p, station_manager, /tasks/:id, reassign

# 系统管理员权限（超级权限）
p, admin, /*, *
p, admin, /geofences, create
p, admin, /geofences/:id, update
p, admin, /geofences/:id, delete
p, admin, /stations, create
p, admin, /users, manage
p, admin, /roles, manage
```

**优势**：
- 权限继承自动处理（无需重复配置）
- 灵活支持角色升级（修改用户角色即可）
- 细粒度控制（页面级 + 按钮级权限）

### 3.5 部署简化（适合社区小型应用）

**合并方案部署架构**：
```

    ↓

    ↓

    ↓ 根据 JWT Token 中的 role 字段
```

**分离方案部署架构**：
```
Internet
    ↓
Nginx (反向代理)
    ├─ /b-end → b-end 前端应用
    └─ /admin → admin 前端应用

需要：
  - 2个子路径配置
  - 2套独立部署
  - 2份 CORS 配置
  - 2份环境变量
```

**优势**：
- 减少 Nginx 配置复杂度
- 单一应用包，简化版本管理
- 降低运维成本（适合社区场景，服务器资源有限）

## 四、技术实现方案

### 4.1 Casbin 权限守卫

```typescript
// router/guards.ts
import { newEnforcer, Enforcer } from 'casbin'
import { Router } from 'vue-router'

let enforcer: Enforcer

export async function setupPermissionGuard(router: Router) {
  // 初始化 Casbin Enforcer
  enforcer = await newEnforcer(
    '/public/casbin/model.conf',
    '/public/casbin/policy.csv'
  )

  router.beforeEach(async (to, from, next) => {
    // 跳过白名单路由
    if (to.meta.allowAnonymous) {
      return next()
    }

    const authStore = useAuthStore()
    const userRole = authStore.role
    const resource = to.path
    const action = to.meta.action || 'read'

    // Casbin 权限检查
    const allowed = await enforcer.enforce(userRole, resource, action)

    if (allowed) {
      next()
    } else {
      console.warn(`权限拒绝: ${userRole} → ${resource}:${action}`)
      next({
        name: 'Forbidden',
        query: { redirect: to.fullPath }
      })
    }
  })
}

// 导出权限检查函数供组件使用
export async function checkPermission(
  resource: string,
  action: string
): Promise<boolean> {
  const authStore = useAuthStore()
  return await enforcer.enforce(authStore.role, resource, action)
}
```

### 4.3 权限指令（v-permission）

```typescript
// directives/permission.ts
import { Directive, DirectiveBinding } from 'vue'
import { checkPermission } from '@/router/guards'

export const vPermission: Directive = {
  async mounted(el: HTMLElement, binding: DirectiveBinding) {
    const { resource, action } = binding.value

    const hasPermission = await checkPermission(resource, action)

    if (!hasPermission) {
      // 移除元素或隐藏
      el.style.display = 'none'
      // 或者 el.remove()
    }
  }
}

// 注册指令
// main.ts
import { vPermission } from '@/directives/permission'
app.directive('permission', vPermission)
```

### 4.4 权限 Composable（组合式API）

```typescript
// composables/usePermission.ts
import { computed } from 'vue'
import { useAuthStore } from '@/store/auth'
import { checkPermission } from '@/router/guards'

export function usePermission() {
  const authStore = useAuthStore()

  const hasPermission = async (resource: string, action: string) => {
    return await checkPermission(resource, action)
  }

  const hasAnyPermission = async (permissions: Array<{ resource: string, action: string }>) => {
    const results = await Promise.all(
      permissions.map(p => checkPermission(p.resource, p.action))
    )
    return results.some(r => r)
  }

  const hasAllPermissions = async (permissions: Array<{ resource: string, action: string }>) => {
    const results = await Promise.all(
      permissions.map(p => checkPermission(p.resource, p.action))
    )
    return results.every(r => r)
  }

  return {
    hasPermission,
    hasAnyPermission,
    hasAllPermissions
  }
}

// composables/useTaskPermission.ts（特定领域权限）
export function useTaskPermission() {
  const { hasPermission } = usePermission()

  const canClaimTask = computed(async () =>
    await hasPermission('/tasks/:id', 'claim')
  )

  const canAssignTask = computed(async () =>
    await hasPermission('/tasks/:id', 'assign')
  )

  const canCompleteTask = computed(async () =>
    await hasPermission('/tasks/:id', 'complete')
  )

  const canReassignTask = computed(async () =>
    await hasPermission('/tasks/:id', 'reassign')
  )

  return {
    canClaimTask,
    canAssignTask,
    canCompleteTask,
    canReassignTask
  }
}
```

## 五、风险分析与缓解方案

### 5.1 风险：代码耦合度增加

**问题描述**：
- 工作人员和管理员代码在同一个项目中，可能导致边界不清晰
- 修改管理员功能时可能影响工作人员功能

**缓解方案**：
1. **严格的目录结构**：
   - `views/staff/` 和 `views/admin/` 物理隔离
   - `views/common/` 用于共享组件，明确标注

2. **使用 Composition API 提取共享逻辑**：
   ```typescript
   // composables/useTaskList.ts
   export function useTaskList(scope: 'personal' | 'station' | 'global') {
     // 共享的任务列表逻辑
     // 根据 scope 参数加载不同范围的数据
   }
   ```

3. **代码审查**：
   - Git 分支策略：`feature/staff/*` 和 `feature/admin/*` 分开
   - Pull Request 必须明确影响范围

---

### 5.2 风险：路由配置复杂度增加

**问题描述**：
- 单一应用中包含所有角色路由，配置可能变得复杂
- 动态路由加载逻辑需要额外维护

**缓解方案**：
1. **按角色拆分路由文件**：
   ```typescript
   // router/staff.routes.ts
   export const staffRoutes = [...]

   // router/admin.routes.ts
   export const adminRoutes = [...]

   // router/index.ts
   const routes = [
     ...staffRoutes,
     ...adminRoutes
   ]
   ```

2. **路由配置自动化**：
   ```typescript
   // 从后端获取用户权限 → 动态注册路由
   router.beforeEach(async (to, from, next) => {
     if (!routesRegistered) {
       const userPermissions = await fetchUserPermissions()
       const allowedRoutes = filterRoutesByPermission(allRoutes, userPermissions)
       allowedRoutes.forEach(route => router.addRoute(route))
       routesRegistered = true
     }
     next()
   })
   ```

   ```typescript
       role: authStore.role,
       resource: to.path,
       action: to.meta.action,
       allowed
     })

     next()
   })
   ```

## 六、性能评估

### 6.1 打包体积对比

| 方案 | 工作人员端包大小 | 管理端包大小 | 总大小 |
|------|----------------|-------------|--------|
| 分离方案 | 800 KB | 1200 KB | 2000 KB |
| 合并方案（未优化） | - | 1800 KB | 1800 KB |
| 合并方案（代码分割） | 首屏 600 KB + 按需加载 | - | 1700 KB |

**结论**：合并方案通过代码分割后，总体积减少 15%。

## 七、迁移路径（未来考虑）

如果未来需求变化（如用户量暴增至 10万+），可以平滑迁移到分离架构：

### 7.1 迁移触发条件

- 用户量 > 10万（并发量显著增加）
- 工作人员端和管理端发布周期差异巨大
- 团队规模扩大，需要独立团队维护

### 7.2 迁移步骤

1. **提取共享库**：
   ```bash
   npm create @myorg/shared-components
   npm create @myorg/shared-utils
   npm create @myorg/shared-types
   ```

2. **拆分应用**：
   - 将 `views/staff/` 迁移到 `staff-portal` 项目
   - 将 `views/admin/` 迁移到 `admin-portal` 项目
   - `views/common/` 发布为 npm 包

3. **Casbin 配置保持不变**：
   - 权限模型无需修改
   - 两个应用共享同一套权限策略
